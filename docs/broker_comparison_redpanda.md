# 메시지 브로커 3파전: Kafka vs NATS vs Redpanda

**작성일:** 2026-01-19  
**목적:** 기존 Kafka/NATS 비교에 Redpanda를 추가하여, 차세대 고성능 브로커 도입을 위한 심층 비교 분석.

---

## 1. Redpanda란 무엇인가?
**"C++로 작성된 Zookeeper 없는 Kafka"**
Redpanda는 Kafka API와 100% 호환되도록 설계되었지만, 내부는 완전히 다릅니다. JVM(자바 가상 머신)을 걷어내고 C++와 Seastar 프레임워크를 사용하여 **하드웨어 성능을 극한으로 끌어올린** 브로커입니다.

*   **핵심 철학:** "Kafka는 훌륭하지만 너무 무겁고 운영이 어렵다. 우리는 Kafka API를 그대로 쓰면서 가볍고 빠르게 만든다."

---

## 2. 3파전 상세 비교 (Kafka vs NATS vs Redpanda)

| 구분 | Apache Kafka | NATS JetStream | Redpanda |
| :--- | :--- | :--- | :--- |
| **언어/런타임** | Java / Scala (JVM) | Go (Single Binary) | C++ (Single Binary) |
| **아키텍처** | Thread Pool 모델 (Context Switching 많음) | Goroutine (경량 스레드) | **Thread-per-Core** (Lock-free, 비동기) |
| **운영 복잡도** | **상** (튜닝 포인트 많음) | **하** (설정 파일 하나) | **하** (단일 바이너리, rpk 툴 제공) |
| **성능 (Latency)** | 보통 (GC로 인한 튀는 현상 있음) | **최상** (매우 낮음) | **최상** (P99 Latency가 매우 안정적) |
| **API 호환성** | - | 독자 프로토콜 | **Kafka API 100% 호환** |
| **레퍼런스 양** | ⭐⭐⭐⭐⭐ (압도적, 구글링하면 다 나옴) | ⭐⭐⭐ (꾸준히 증가 중) | ⭐⭐ (상대적으로 적음, 공식 문서 의존) |
| **라이선스** | Apache 2.0 (완전 무료) | Apache 2.0 (완전 무료) | **BSL** (소스 공개, 상용 서비스 제한 있음) |

## 3. 저장소 및 I/O 아키텍처 비교 (Storage Engine)

데이터를 디스크에 저장하고 불러오는 방식의 결정적인 차이입니다.

### 3.1 Apache Kafka: "OS를 믿는다" (Page Cache)
*   **방식:** 애플리케이션 레벨에서 캐싱을 하지 않고, 운영체제(OS)의 **Page Cache**에 전적으로 의존합니다.
*   **장점:** 메모리 관리를 OS에게 위임하여 효율적입니다. **Zero-Copy** 기술로 디스크->네트워크 전송 속도가 빠릅니다.
*   **단점:** OS가 언제 데이터를 디스크에 실제로 쓸지(Flush) 완벽하게 제어하기 어렵습니다. (데이터 안정성을 위해 `fsync` 설정을 튜닝해야 함)

### 3.2 Redpanda: "우리가 직접 한다" (Direct I/O & DMA)
*   **방식:** OS Page Cache를 **우회(Bypass)**하고 디스크에 직접 씁니다(**O_DIRECT**).
*   **장점:** 데이터 유실 가능성을 원천 차단합니다. JVM GC(가비지 컬렉션)가 없어서 대용량 처리 시에도 지연 시간(Latency)이 튀지 않고 매우 일정합니다.
*   **Tiered Storage:** 로컬 디스크는 '캐시'처럼 쓰고, 원본 데이터는 **S3/GCS** 같은 저렴한 오브젝트 스토리지에 무한대로 저장하는 기능이 핵심입니다.

### 3.3 NATS JetStream: "유연함" (Hybrid)
*   **방식:** 스트림 생성 시 **Memory** 또는 **File** 중 선택할 수 있습니다.
*   **특징:** 중요하지 않은 데이터는 메모리에만 둬서 극한의 속도를 낼 수 있고, 중요한 데이터는 파일에 저장합니다. Kafka처럼 복잡한 세그먼트 관리보다는 단순함을 지향합니다.

## 4. 심층 분석: Redpanda의 무기

### 4.1 Kafka 호환성 (Drop-in Replacement)
Redpanda의 가장 큰 장점입니다. **기존에 Kafka용으로 짜놓은 코드, 사용하던 Kafka Connect, Kafka UI, 모니터링 도구를 단 한 줄도 안 고치고 그대로 쓸 수 있습니다.**
*   **벤더 락인 없음:** Redpanda를 쓰다가 맘에 안 들면 언제든 Kafka로 돌아갈 수 있고, 반대도 가능합니다.

### 4.2 Thread-per-Core 아키텍처
CPU 코어 하나당 스레드 하나를 딱 고정(Pinning)해서 씁니다. 락(Lock)을 거의 안 쓰고 컨텍스트 스위칭 비용이 없습니다.
*   **결과:** 고성능 NVMe SSD와 최신 CPU가 있는 환경에서는 Kafka보다 10배 이상의 처리량을 보여주기도 합니다.

## 5. 레퍼런스 및 생태계 비교 (현업 중요)

*   **Kafka:**
    *   **자료:** StackOverflow, 블로그, 책이 넘쳐납니다. 어떤 에러가 터져도 검색하면 나옵니다.
    *   **인력:** Kafka 할 줄 아는 개발자 채용이 쉽습니다.

*   **NATS:**
    *   **자료:** 공식 문서가 매우 잘 되어 있고, Slack 커뮤니티가 활발합니다. 하지만 한글 자료는 부족합니다.
    *   **인력:** Go 언어 개발자들 사이에서는 인기가 높습니다.

*   **Redpanda:**
    *   **자료:** 역사가 짧아 자료가 적습니다. 공식 문서와 Redpanda 커뮤니티 Slack에 의존해야 합니다. 트러블슈팅 시 **"이거 왜 안 돼요?" 했을 때 답을 찾기 어려울 수 있습니다.**
    *   **생태계:** Kafka 생태계를 그대로 훔쳐(?) 쓰므로, 도구 부족 문제는 없습니다.

## 6. 라이선스 주의사항 (Redpanda BSL)

Redpanda는 **BSL (Business Source License)**를 따릅니다.
*   **무료:** 사내 시스템, 납품용 솔루션(On-premise 설치)에는 대부분 무료로 사용 가능합니다.
*   **유료/제한:** **"Redpanda를 클라우드 서비스(SaaS)로 남에게 돈 받고 제공하는 경우"**는 금지됩니다. (예: AWS가 Redpanda 서비스를 맘대로 못 만들게 막음)
*   **결론:** 일반적인 SI 납품이나 기업 내부 사용은 문제없으나, 법무팀 확인이 필요할 수 있습니다.

## 7. 최종 결론: 언제 무엇을 써야 할까?

### ✅ Redpanda 선택 시나리오
1.  **"Kafka를 써야 하는데 운영이 너무 힘들다."** (Zookeeper 싫고, JVM 튜닝 지쳤을 때)
2.  **"Kafka 코드를 그대로 쓰면서 성능만 높이고 싶다."**
3.  **"고성능 하드웨어(NVMe)를 100% 활용하고 싶다."**

### ❌ Redpanda 보류 시나리오
1.  **"완벽한 오픈소스(Apache 2.0)여야만 한다."** (라이선스 이슈)
2.  **"문제가 생겼을 때 구글링으로 해결하고 싶다."** (레퍼런스 부족) -> Kafka가 안전.
3.  **"그냥 가볍고 단순한 통신만 하면 된다."** -> NATS가 더 가볍고 쌉니다.

### 🏁 요약
*   **NATS:** Kafka와 완전히 다른 길. **"가볍고 빠른 MSA 통신"**
*   **Redpanda:** Kafka와 같은 길을 가는 고성능 스포츠카. **"Kafka의 상위 호환 대체재"**
*   **Kafka:** 든든한 대형 세단. **"표준, 안정성, 방대한 자료"**
