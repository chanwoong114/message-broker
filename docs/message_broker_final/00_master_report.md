# 메시지 브로커 최종 비교 분석 보고서: RabbitMQ vs Redpanda

**작성일:** 2026-01-26  
**대상 솔루션:** RabbitMQ (Stream/Classic), Redpanda (Kafka API)  
**환경:** Kubernetes (Kind), Prometheus, Grafana, Redpanda Console

---

## 1. 개요 (Executive Summary)
본 보고서는 현대적인 마이크로서비스 아키텍처 및 데이터 파이프라인 구축을 위한 두 핵심 메시지 브로커인 **RabbitMQ**와 **Redpanda**를 비교 분석합니다. 단순 이론 비교를 넘어 실제 Kubernetes 환경에서 **메시지 적재, 소비, 히스토리 관리, 그리고 모니터링 편의성**을 직접 실습하고 검증한 결과를 담고 있습니다.

---

## 2. 핵심 아키텍처 및 스펙 비교

### 2.1. 기술 비교표
| 특징 | RabbitMQ (Stream) | Redpanda (Kafka API) |
| :--- | :--- | :--- |
| **기본 모델** | 스마트 브로커 (Smart Broker) | 분산 로그 (Log-based) |
| **저장 방식** | OS Page Cache & Zero-copy | **Direct I/O & DMA** (최적화) |
| **메시지 보존** | 기본 휘발성 (Stream 사용 시 보존) | **기본 영구 보존** (Tiered Storage 지원) |
| **운영 사양** | 메모리 중심 (Fast SSD 권장) | **NVMe SSD / XFS 필수 권장** |
| **UI 편의성** | 낮음 (기본 UI 기능 제약) | **매우 높음** (Redpanda Console) |

### 2.2. 인프라 요구 사양 (Prod 권장)
*   **Redpanda:** 4+ Cores, 16GB+ RAM, **NVMe SSD** (XFS 파일시스템). 하드웨어 성능을 끝까지 뽑아내는 구조.
*   **RabbitMQ:** 4+ vCPU, 8GB+ RAM, Fast SSD. 복잡한 라우팅 처리 시 메모리 증설 필수.

---

## 3. RabbitMQ 심층 검증 (Classic vs Stream)

실습을 통해 확인된 두 방식의 차이는 **"데이터를 대하는 철학"**의 차이입니다.

### 3.1. 주요 실습 결과
*   **Classic Queue:** 메시지를 읽고 Ack 하는 순간 **삭제**됨. `Ready` 숫자가 줄어드는 것이 "정상 처리"의 신호.
*   **Stream Queue:** 메시지를 읽어도 **삭제되지 않음.** `Ready` 숫자는 누적 데이터 양을 의미함. 
*   **히스토리 재생:** Stream Queue에서만 `offset: first` 옵션을 통해 과거 데이터를 처음부터 다시 읽기(Replay)가 가능함을 확인.

### 3.2. 운영 시사점: Lag 모니터링의 어려움
RabbitMQ Stream은 "전체 메시지"와 "내가 읽은 오프셋" 정보를 별도로 관리하며, 기본 UI에서 이를 뺄셈하여 **지연(Lag)** 수치를 명시적으로 보여주지 않습니다. 운영자가 시스템 구조를 깊이 이해해야 장애(지연)를 판단할 수 있다는 단점이 있습니다.

---

## 4. Redpanda 심층 검증 (모니터링과 관측성)

Redpanda는 "데이터가 무엇인가"를 보여주는 능력에서 압도적인 우위를 보였습니다.

### 4.1. Redpanda Console (UI)의 강점
*   **메시지 브라우징:** CLI 없이 웹에서 즉시 메시지 본문(JSON 등)을 검색하고 확인 가능.
*   **직관적인 Lag 표시:** `Consumer Groups` 메뉴에서 컨슈머별 **지연(Lag) 개수**를 숫자로 즉시 노출. "밀린 숙제"가 몇 개인지 1초 만에 파악 가능.

### 4.2. Grafana 통합 아키텍처
*   Redpanda 브로커 자체는 Lag 메트릭을 기본 제공하지 않으나, **`Kafka Lag Exporter`**를 통해 해결 가능.
*   **리소스 소요:** Exporter 운영에 약 **512Mi**의 메모리 필요.
*   **결과:** Grafana 대시보드에서 Lag의 발생과 해소 과정을 실시간 그래프로 완벽하게 관측 가능.

---

## 5. 지연(Lag)의 정의 및 장애 판단

*   **Lag의 정의:** `(프로듀서가 쓴 총 데이터 수) - (컨슈머가 처리한 데이터 수)`. 즉, **"아직 처리하지 못한 뒤처진 메시지 개수"**.
*   **장애 판단 기준:**
    1.  **Lag = 0:** 실시간 처리 중 (정상).
    2.  **Lag 지속적 증가:** 컨슈머 처리 속도가 생산 속도보다 느림 (성능 병목).
    3.  **Lag = 생산 속도와 동일하게 증가:** 컨슈머 중단 (장애).

---

## 6. 최종 결론 및 제언

### ✅ Redpanda를 추천하는 경우
*   **운영 가시성**이 최우선일 때 (누구나 웹에서 데이터를 쉽게 보고 장애를 판단해야 함).
*   **데이터 파이프라인 및 이벤트 소싱**이 주 목적인 대규모 스트리밍 환경.
*   고성능 하드웨어(NVMe)를 갖추고 지연 시간을 극도로 줄여야 할 때.

### ✅ RabbitMQ를 추천하는 경우
*   **복잡한 라우팅 로직** (Header, Topic 매칭 등)이 필요할 때.
*   기존 AMQP 기반 시스템이 이미 구축되어 있고, 부분적으로만 로그 기능(Stream)이 필요할 때.
*   가벼운 워크로드에서 적은 리소스로 브로커를 운영하고 싶을 때.

---

**[최종 의견]**
실습 결과, **운영 편의성과 관측성(Observability)** 면에서는 **Redpanda**가 압도적으로 우수합니다. 특히 "Lag" 중심의 모니터링이 직관적이어서 대규모 시스템 운영 시 장애 대응 속도를 획기적으로 줄일 수 있습니다. 반면 RabbitMQ는 전통적인 메시징 패턴에 강점이 있으나, Stream 기능을 본격적으로 쓰기에는 UI/모니터링 도구가 보완되어야 할 지점이 많습니다.
